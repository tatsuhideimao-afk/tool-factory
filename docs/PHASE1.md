# Phase 1 — 30日実測プロトコル

仕様 6章の実行手順。**この文書の判定基準は開始前に確定させたものであり、後から動かさない。**

---

## 何を測るのか

収益シミュレーションの前提値には裏付けがない。だから Phase 1 の目的は収益ではなく、
**「Webツール1本あたり自然検索でどれだけ人が来るか」** という、以降のすべての試算の
土台になる数字を1つ実測することにある。

測るのは1点だけ：**宣伝を一切しない状態で、30日間にサイト全体で何UU積むか。**

---

## 実験条件

| 項目 | 条件 |
|---|---|
| 公開するもの | Webツール3本（`json-format` / `csv-json` / `pdf-merge`） |
| 期間 | 公開日を Day 0 として30日間 |
| 宣伝 | **一切しない。** SNS投稿・被リンク獲得・拡散依頼・知人への共有をすべて禁止 |
| コード変更 | **しない。** 30日間は触らない（バグ修正を除く。修正した場合は記録する） |
| 追加公開 | しない。4本目を足すと1本あたりの流入が測れなくなる |
| 計測 | `06-measure` が毎日 03:00 JST に自動記録 |

宣伝を禁止するのは意地悪ではなく、**「自然流入だけで何UU積むか」以外の変数を混ぜないため**。
1本でも被リンクを付けた時点で、この30日の数字は他の企画の見積もりに使えなくなる。

## 30日後の判定基準（動かさないこと）

| 30日後のサイト全体UU | 意味 | 次のアクション |
|---|---|---|
| **50未満** | 自然流入がほぼゼロ。量産モデルそのものが成立していない | **Phase 2 に進まない。** マイクロSaaS方向へ設計をやり直す |
| **50〜299** | 弱いが流入はある | 企画発掘の質が課題。`01-research` を作り込んでから再測定 |
| **300以上** | 量産の前提が成立 | Phase 2（全モジュール実装＋拡張昇格）へ進む |

この基準を満たさないまま Phase 2 に進むことを禁止する。

---

## 判定に使う数字の出し方

```bash
pnpm report    # 直近30日のサイト全体UUとツール別の内訳が出る
```

`06-measure` が記録しているのは Cloudflare Web Analytics の **visits（セッション数）**。
Cookieless な計測なので厳密なユニークユーザーではない。
**判定は最初から最後まで同じ指標（visits）で通すこと。** 途中で別の指標に乗り換えると、
基準値との比較が成立しなくなる。

## 30日の途中でやってよいこと・いけないこと

**やってよい:**

- 落ちているページの修正（記録を残す）
- `07-report` の通知を眺める
- Phase 2 の設計を紙の上で進める

**やってはいけない:**

- ツールの追加
- SNS投稿、被リンク獲得、知人への共有
- 判定基準の変更
- 「まだ早い」という理由での期間延長（30日で切る）

---
